# ADR-0005 — Document the API in JSDoc and read it from the manifest

- **Status:** Accepted
- **Date:** 2026-10-31
- **Concerns:** ADR-0001, ADR-0004

## Context

`custom-elements.json` was generated but empty of meaning: no description, no tag name (the analyzer does not see through the `define()` helper), and internal state such as `expanded` or `slottedDescription` listed as public attributes because `static properties` declares it next to the real ones. No story named its component, so `setCustomElementsManifest` fed nothing. The React element wrappers and the Vue global component types were written by hand from the element classes, a third description of the same API.

The repository forbids comments in code. Public JSDoc on a custom element is not narration: it is the only input the manifest analyzer reads for summaries, slots, parts, custom properties and events.

## Decision

- **Every element carries public JSDoc**, in English: a class block with a description, `@summary`, `@tag lu-<name>`, `@slot`, `@csspart`, `@cssprop` and `@fires {CustomEvent<Detail>} lu-<name> - …`, and a `/** … */` line on the `declare` of every public property, which the attribute inherits. Nothing in function bodies, nothing on private or protected members. This is the one exception to the no-comment rule for code.
- **`custom-elements.json` holds the public API only.** `scripts/manifest-plugins.js` drops private and protected members after inheritance, with the attributes of state properties, and reads `@deprecated` at the end of an `@fires`, `@slot`, `@csspart` or `@cssprop` line.
- **The manifest is the source of three outputs**: the Storybook props tables (each story declares `component: 'lu-<name>'` and `tags: ['autodocs']`), `src/react/elements.ts` (one `createComponent` per element, its events named `on` + the camel-cased name without `lu-`) and `src/vue/elements.ts` (the `GlobalComponents` map with typed `onLu…` event props, and `LumenElementTag`). Both files are generated by `pnpm generate` and ignored by git.
- **The hand-written React API stays hand-written.** `Button`, `Dialog` with `onOpenChange(open)`, `DataTable` and the floor-0 components translate the elements into React idioms; a generator would have to encode each of those choices.
- `src/manifest.test.ts` fails when an element, attribute, property, event, slot, part or custom property has no description, or an event is not `lu-*` with a typed `CustomEvent`.

## Consequences

- A property added without a description fails the tests; one added with a description reaches Storybook, React and Vue without another edit.
- The element classes still carry the TypeScript types the adapters use; the manifest adds names, events and descriptions, not types. An event detail type named in `@fires` must be exported from `src/index.ts`, or the generated adapters do not compile.
- `lu-pickup`, which `lu-draggable` sends to `lu-drag-area`, is not documented: it is a private protocol, even though it bubbles out.
- The default slot does not appear in the Storybook props table, which ignores unnamed slots; the element description mentions it.

## Alternatives considered

### Keep the JSDoc out and write `parameters.docs` per story

Descriptions in stories reach Storybook only; the manifest stays empty for editors, the React and Vue types and any tool that reads `customElements` from `package.json`.

### Generate the whole React adapter from the manifest

What `@lit/react` wrappers alone give: `open` and `lu-open-change` instead of `open` and `onOpenChange(open)`, and no floor-0 components. That is the API Ariane would have to rewrite against.

## Revisit if

The analyzer learns to read `define()` calls and Lit's `state: true`, or the React adapter's idiomatic layer becomes regular enough to describe as data.
